第 15 章 部署与运维

本章目标

  • 理解生产镜像的两个决定：多阶段构建、standalone 产物
  • 复述部署时序：迁移先行、健康检查、密钥注入，以及每一步的理由
  • 拿到一份可以直接用的上线检查清单，并理解每条背后的坑

15.1 镜像：只装运行需要的东西

参考实现的 Dockerfile 是多阶段构建：

deps 阶段：装全部依赖（含开发依赖）
build 阶段：next build，产出 standalone
runner 阶段：只拷贝 standalone 产物 + 静态资源，以非 root 用户运行
tools 阶段：只含迁移脚本与 schema，用于一次性迁移任务（第 2 章）
  • standalone 产物：Next 构建出自带最小依赖的独立目录，运行镜像不需要完整的 node_modules，镜像从 GB 级降到百 MB 级。部署快、攻击面小。
  • 运行镜像不带源码工具链：没有编译器、没有开发依赖。出事时攻击者能用的东西越少越好。
  • 非 root 运行：容器内进程以普通用户跑，容器逃逸的损失被限制。
  • 构建不连数据库：第 2 章守住的那条线在这里兑现——next build 全程不需要数据库与生产密钥，CI 里就能构建出与生产完全相同的镜像。

15.2 部署时序

一次标准部署的顺序（与第 2 章的 compose 编排是同一套逻辑）：

  1. 构建镜像并打上版本标签（git commit 短哈希即可），推送到镜像仓库。
  2. 在新版本接流量之前，单独运行迁移任务（tools 镜像）：迁移成功才继续，失败就停在旧版本。
  3. 启动新版本，健康检查（/api/health，第 2 章）通过后才把流量切过去。
  4. 保留上一个版本的镜像与数据库迁移的回退方案：应用回滚 = 切回旧镜像；数据库迁移尽量写成向后兼容的（先加列、后删列分两次发布），这样旧版本能跑在新结构上，回滚才真的可行。

迁移与回滚的这条纪律最容易被忽略：一次发布里既删列又改代码，出了问题旧代码连不上新结构，回滚之路当场断掉。

15.3 密钥与配置注入

  • 密钥（AUTH_SECRET、DATABASE_URL、支付密钥）通过部署平台的环境变量/密钥管理注入，不写进镜像、不进 git。镜像是公开可复制的，密钥进镜像等于公开。
  • 第 2 章的 env 模块在生产环境缺密钥直接拒绝启动——部署后第一件事就是看它有没有正常起来，这正是那条校验的价值时刻。
  • 不同环境（生产/预发）用同一镜像、不同 env。这保证了「测过的产物」与「上线的产物」是同一个东西。

15.4 上线检查清单

参考实现 README 的「上线前还需要」一节，加上本教程各章的结论，汇总成这份清单。每条都对应一个真实会翻车的点：

  • [ ] HTTPS 就绪：cookie 的 Secure 推导依赖它（第 2、6 章）；没有 HTTPS 不要上线登录功能。
  • [ ] 密钥全部轮换为生产值：AUTH_SECRET ≥ 32 字符随机值；不存在任何 dev 默认值。
  • [ ] 会话撤销方案明确：JWT 方案的撤销缺口（第 6 章）已评估：缩短有效期 / token 版本号 / 换数据库会话，三选一或明确接受风险。
  • [ ] 支付回调域名可达且验签通过：用支付商的测试模式实打一笔小额，确认 webhook 落地、金额核对、订单转 paid（第 12 章）。
  • [ ] 迁移在预发环境演练过：包括从旧版本数据升级，而不是只在空库上跑。
  • [ ] 数据库备份与恢复演练：有自动备份，且真的恢复过一次。没恢复过的备份叫希望，不叫备份。
  • [ ] 未支付订单的超时关闭任务在跑：否则库存被 pending 订单长期占用（第 12、13 章）。
  • [ ] 日志与告警：支付失败、webhook 验签失败、迁移失败这三类事件有人能看到。
  • [ ] 限流与滥用防护：登录、下单接口有基本限流（网关或应用层）。教程的参考实现未内置，属于明确的生产加项。
  • [ ] 对账任务：支付商结算单与本地订单的每日比对已排期（第 12 章）。

常见误区

  • 「能跑起来 = 能上线」：能跑只证明了功能。密钥、HTTPS、备份、回滚、告警这些「不出事看不见」的东西，才是上线的定义。
  • 「迁移和代码一次发布最省事」：省的是几分钟，赌上的是回滚能力。结构变更与代码变更分开发布。
  • 「备份开了自动 = 安全」：没做过恢复演练的备份，恢复时才发现格式/密钥/权限有问题，是运维界最经典的事故剧情。

  2. 拿 15.4 的清单逐条对照参考实现，标出每条是「已满足 / 需配置 / 需开发」，需开发的写一句话方案。
