第 10 章 客户端状态与服务端状态：以购物车为例

本章目标

  • 理解一类通用问题：跨越「未登录 → 已登录」的状态如何平滑过渡
  • 看懂游客购物车 + 登录合并的设计，以及 cookie 中标识符的校验
  • 理解数量一类边界为什么必须由服务端钳制，而不是信前端

购物车是「服务端状态」的典型样本：它要跨页面、跨设备、跨登录态存在，还要在结账时被服务端完全信任。本章的方法适用于一切类似状态（草稿、收藏、待办清单）。

10.1 先问业务：未登录能不能先攒着？

参考实现的决定是：游客可以加购、可以结账（结账时填邮箱和地址即可）。于是它需要一等公民的「游客购物车」：购物车记录先建着，userId 为空，靠 cookie 里的 cart id 认领。找车逻辑（src/features/cart/cart-store.ts）因此分两条路：

export async function findCartId(): Promise<string | null> {
  const session = await getSession();
  if (session) {
    // 登录用户：按 userId 找他的购物车
    const [cart] = await db.select({ id: carts.id }).from(carts)
      .where(eq(carts.userId, session.userId)).limit(1);
    return cart?.id ?? null;
  }
  // 游客：读 cookie，并校验它真的是个 UUID、且库里存在这辆车
  const raw = (await cookies()).get(CART_COOKIE)?.value;
  if (!raw || !UUID_RE.test(raw)) return null;
  // …
}

两个要点：

  • cookie 里的标识符是用户输入：先正则验形状，再查库确认存在，不能拿来就信。一切来自客户端的值——cookie、header、URL、表单——同理。
  • 读与建拆成两个函数：findCartId 只读、渲染期可调用；getOrCreateCartId 会写 cookie，只能在 Server Action 里调用（渲染期写 cookie 在 Next 里是禁止的）。这个拆分是被框架的渲染规则逼出来的正确形状。

如果业务决定「必须登录才能加购」，结构立刻简化：购物车行直接以 user_id 为键，没有游客态、没有合并。这提醒我们：状态管理的复杂度首先来自业务决定，其次才是技术。先把业务前提写下来，再选结构。

10.2 登录合并：游客态平滑过渡到用户态

游客逛了半天攒了五件商品，然后登录——如果登录后购物车变空，体验当场崩掉。参考实现的 mergeGuestCartInto(userId) 在注册/登录成功后立刻执行：

  • 用户还没有购物车：直接把游客车的 userId 改成他，「认领」完成，零数据搬运。
  • 用户已有购物车：逐行把游客车的数量累加进用户车（同一商品用 onConflictDoUpdate 做 quantity = quantity + 游客数量），然后删掉游客车、清掉 cookie。
  • 全程一个事务：中途失败就整体回滚，不会出现「一半合并一半没合」的中间态。

这个模式可以推广到一切「匿名态攒数据、登录后归属到账号」的场景：先认领、再合并、最后清理匿名标识。

10.3 数量边界：服务端钳制，不信前端

加购 action（src/features/cart/actions.ts）：

const MAX_PER_LINE = 20;
// 校验：zod 先卡 productId 是 uuid、quantity 在 1..20
// 再查商品：不存在、未上架、无库存 → 直接返回，什么都不做
const next = Math.min((existing?.quantity ?? 0) + quantity, product.stock, MAX_PER_LINE);

三层钳制：单次提交上限（zod）、单行总量上限（20）、库存上限（Math.min 里带上 product.stock）。为什么加购时就钳到库存？因为购物车是结账的预演，越早把数量拉回现实，结账时「库存不足」的惊吓越少。当然结账时还要再验一次（第 11 章）——加购到结账之间库存随时可能被别人买走，购物车里的数字只是「当时的意愿」，不是预留。

另一个并发细节：同一用户双击或多标签页同时加购，参考实现靠单条 INSERT … ON CONFLICT 的原子性 + Math.min 钳制保证结果不越界（并发下可能少加一件，但不会加出超库存的脏数据）。如果业务要求严格串行，可以在事务里先锁住用户行（SELECT … FOR UPDATE），让同一用户的购物车操作排队执行——并发控制的强度要匹配业务对正确性的要求：购物车数量差一件可以接受，订单库存差一件不行（下一章）。

常见误区

  • 「这类状态放 localStorage 就行」：换设备就丢、服务端结账时还得全部重验重建。服务端状态放数据库，客户端只存「这份状态是谁的」标识。
  • 「前端 max 属性限制了数量，后端不用管」：max 是给诚实用户的提示，不是约束。约束只认服务端钳制。
  • 「加购成功就等于预订了库存」：购物车不预留库存是通行做法（否则加购不买的人能把库存锁死）。结账那一刻的校验才是真的——下一章的主题。

本章练习

  1. 以游客身份加购两件商品，再注册新账号，验证购物车被合并、数量正确；再造一个「两边都有同一商品」的场景验证累加。
  2. 找合并逻辑的边界情况：游客车和用户车有同一商品、且合计超过单行上限 20 时，现在的代码会怎样？需要修吗？
  3. 思考题：把购物车改成「必须登录」后，cart-store.ts 里哪些函数可以删掉、表结构可以怎么简化？动手删一遍，体会业务前提对代码量的影响。
