第 14 章 测试策略

本章目标

  • 理解测试投入的分配原则：先测领域层，再测关键流程，页面最后
  • 看懂参考实现的测试长什么样：纯函数单测 + 关键校验的回归测试
  • 理解「测试是架构的验收单」：分层做得好，测试自然好写

14.1 先测哪里：按「出错代价 × 变化频率」排序

测试资源永远有限，排序依据是出错的代价：

  1. 领域层纯函数（第 4 章）：金额计算、定价规则、状态流转。出错直接赔钱，且规则经常微调。它们是纯函数，测起来最便宜——给定输入、断言输出，没有数据库、没有网络。
  2. 校验与安全边界：金额解析的边界输入（"1.005"、"-5"、空串）、登录跳转的 safeNext（//evil.com 必须被拦）、令牌的签发与验签。
  3. 关键写流程的集成测试：下单事务的并发行为（第 11 章）——需要真数据库，成本高，但这是系统最贵的不变量，值得。
  4. 页面与 UI：最后。UI 变化最频繁，端到端测试维护成本最高，只覆盖最核心的几条用户路径（浏览 → 加购 → 结账 → 支付成功）。

这个排序背后的原理是第 1 章的分层：规则越纯、越靠内层，测试越快越稳。一个功能难测，往往不是测试的问题，是它被写错了层——业务规则揉在页面组件里，当然测不动。

14.2 参考实现的测试长什么样

参考实现用 Vitest，测试集中在钱、令牌、校验三处，都是毫秒级跑完的纯逻辑测试。以金额解析为例，测试用例本质上是一张「输入 → 期望」表：

describe("parseMoneyToCents", () => {
  it("正常金额", () => {
    expect(parseMoneyToCents("19.99")).toBe(1999);
    expect(parseMoneyToCents("100")).toBe(10000);
  });
  it("拒绝三位小数、负数与非数字", () => {
    expect(parseMoneyToCents("1.005")).toBeNull();
    expect(parseMoneyToCents("-5")).toBeNull();
    expect(parseMoneyToCents("abc")).toBeNull();
  });
});

写这类测试的窍门：先列边界清单，再逐个变成用例。边界来自规则本身：零、负数、最大值、格式擦边（多一位小数）、空值、类型擦边（数字型字符串 vs 真数字）。第 4 章 totals() 练习里要求你先写用例表，就是在练这个顺序——先想清规则，再写代码，测试自然成形。

令牌测试则覆盖安全语义：过期令牌验不过、篡改过的签名验不过、role 不是 "admin" 时被收敛成 customer（第 6 章的白名单）。

14.3 集成测试：只测最贵的不变量

下单流程的并发测试需要真实 PostgreSQL（可用一个专用的测试库 + 事务回滚隔离）。要断言的不是「接口返回 200」，而是第 11 章的不变量：

  • 库存为 1、两个并发下单 → 恰好一个成功，库存为 0，无负数；
  • 同一幂等键提交两次 → 只有一张订单；
  • 事务中途失败 → 库存、订单、购物车三者都回到下单前。

这类测试写起来贵、跑起来慢，所以要少而精：只钉住「错了就赔钱」的几条。其余逻辑靠领域层单测兜住。

14.4 测试纪律三条

  1. 测试必须能在 CI 里一条命令跑完（参考实现是 npm test + npm run typecheck）。跑不起来的测试等于没有。
  2. 改规则先改测试：定价规则调整时，先更新用例表让测试变红，再改实现变绿。测试是规则的规格说明书，顺序反了它就只是摆设。
  3. 不测框架、不测第三方：不测 Next 的路由能不能跳转、不测 Stripe 的 SDK 能不能发请求。只测你的规则和你的编排。

常见误区

  • 「覆盖率越高越好」：覆盖率是副产品不是目标。把 getter 和页面布局测到 100%，不如下单不变量多测一条。
  • 「先写完功能，有空再补测试」：补测试时规则已成既成事实，测试只能照着实现描红，失去了校验规则的作用。至少领域层要同步写。
  • 「单元测试要 mock 一切」：领域层是纯函数，根本不需要 mock。需要大量 mock 才能测的代码，通常是把外部依赖揉进了规则里——回第 1 章看分层。

本章练习

  1. 为第 4 章练习里你加的定价规则补全单测：先写用例表（至少覆盖零、负数、满额边界 ±1、与优惠码叠加），再运行验证。
  2. 给 safeNext 写测试：至少覆盖 /account（放行）、//evil.com（拦）、https://evil.com（拦）、空值（回落到 /）。
  3. 写下单并发的集成测试（或伪代码级步骤清单）：库存设为 1，并发两个下单，断言 11.3 的三条不变量。
  4. 思考题：为什么第 5 章的目录缓存函数不在本章的测试清单里？它的正确性靠什么保障？（提示：想想它的失效纪律与「查库兜底」。）
