第 11 章 事务与并发控制（全书核心）

本章目标

  • 理解关键写操作为什么必须是一个数据库事务，以及事务里到底放哪些步骤
  • 掌握防超卖的两种打法：条件 UPDATE 与行锁 FOR UPDATE
  • 理解幂等键为什么能防住重复提交，以及事务边界应该划在哪

这一章讲全栈开发里最贵的一课。下单是系统里「错了就要赔钱」的流程：超卖要退款道歉，重复下单要被投诉，金额算错直接亏损。所有机制都是为下面四条不变量服务的。

11.1 不变量先行

  1. 不超卖：库存永远不能扣成负数，哪怕一百个请求同时抢最后一件。
  2. 不重复：用户双击、网络重试、浏览器刷新，不能生成两张订单、扣两次库存。
  3. 价格可信：金额按服务端数据库里的价格算（第 4 章）。
  4. 要么全成，要么全不成：扣了库存却没生成订单（或反过来）是最坏的中间态。

11.2 打法一：条件 UPDATE —— 让数据库原子地判断

参考实现的结账 action 在一个事务里逐行扣库存（src/features/checkout/actions.ts）：

orderId = await db.transaction(async (tx) => {
  // 1) 逐行原子扣库存：UPDATE ... WHERE stock >= qty
  for (const line of cart.lines) {
    const updated = await tx
      .update(products)
      .set({ stock: sql`${products.stock} - ${line.quantity}` })
      .where(and(
        eq(products.id, line.productId),
        eq(products.active, true),
        gte(products.stock, line.quantity),       // ← 关键：库存够才更新
      ))
      .returning({ id: products.id });
    if (updated.length === 0) throw new OutOfStockError(line.name);  // 抛错 = 整个事务回滚
  }
  // 2) 按服务端价格建订单、写订单项快照
  // 3) 清空购物车
  return order.id;
});

精髓在 WHERE stock >= qty：判断和扣减是同一条 SQL。两个并发事务同时抢最后 1 件：数据库逐个执行这条 UPDATE，第一个把库存扣到 0，第二个执行时条件不成立、更新 0 行，代码检查到 updated.length === 0 就抛错回滚。不需要先 SELECT 再判断——「先查后改」之间永远有竞态窗口，条件更新把窗口关死了。

任何一行失败 → 抛异常 → 整个事务回滚：已扣的其他商品库存自动还原，订单不会生成，购物车原样保留。用户收到「『某商品』库存不足，请返回购物车调整」。这就是不变量 4 的落地方式：失败处理不是写一堆补偿代码，而是让事务回滚。

11.3 打法二：行锁 —— 把并发排成队

另一种同样正确的打法是先上锁、再安心地查和改，适合逻辑更复杂的流程（如需要按顺序处理多行、还要查幂等键）：

return transaction(async (c) => {
  // 锁顾客行：同一顾客的相关操作串行化
  await c.query('SELECT id FROM users WHERE id=$1 FOR UPDATE', [userId]);

  // 幂等：同请求键已有订单 → 直接返回那张订单（见 11.4）
  const prior = /* 按 (user_id, request_key) 查已有订单 */;
  if (prior) return prior.id;

  // 按商品 ID 顺序锁定全部涉及的库存行
  const { rows } = await c.query(
    'SELECT … FROM cart_items ci JOIN products p ON p.id=ci.product_id WHERE ci.user_id=$1 ORDER BY p.id FOR UPDATE OF p',
    [userId]);
  for (const r of rows)
    if (!r.active || r.stock < r.quantity) throw new Error('INSUFFICIENT_STOCK');
  // 查到的数据在事务结束前不会被别人改，可以直白地检查、计算、写入…
});

三个细节：

  1. ORDER BY id 再加锁：多个事务锁同一批行时，加锁顺序不一致会互相等成死锁。统一按 id 升序加锁，所有事务以相同顺序拿锁，死锁在结构上被避免。这是行锁打法的必备纪律。
  2. 锁内可以放心地「先查后改」：锁住了行，查到的 stock 在事务结束前不会变，直白的检查反而更易读。行锁与条件更新没有高下之分：无锁的条件更新更轻、适合单点扣减；行锁适合需要在锁内做多步判断的复杂流程。
  3. 锁的粒度决定吞吐：锁用户行只串行化同一个用户，互不影响；锁商品行串行化同一商品的所有买家。按业务的真实竞争点选粒度，别动不动锁全表。

11.4 幂等：防住重复提交

不变量 2 的标准解法是幂等键：

  • 打开结账页时生成一个 UUID 作为本次结账的请求键，随表单一起提交；
  • 订单表给 (user_id, request_key) 加唯一约束（第 3 章）；
  • 下单事务先按请求键查：已有订单就直接返回它（双击、重试、刷新都得到同一个结果）；万一两个请求并发穿过检查，唯一约束会让第二个插入失败，捕获后同样返回已有订单。

分工和第 3 章是同一课：应用检查负责体验（快速返回），数据库约束负责正确性（最终防线）。第 8 章的按钮禁用只是第一层辅助，真正的幂等必须落在服务端。参考实现的支付确认（webhook）用了同一思想的另一形态：带状态条件的原子更新（第 12 章）。

11.5 事务的边界：什么不该放进来

慢的、外部的、不可回滚的操作不进事务。

  • 参考实现的事务只管扣库存、建 pending 订单、清购物车；调支付商创建结账会话在事务提交之后。若支付调用失败，补偿是调用一个显式的逆操作（取消订单并退库存，第 13 章），而不是假装能回滚一件已经发生的事。
  • 同理，发邮件、调第三方 API、写对象存储都不进事务。它们要靠「状态机 + 幂等 + 补偿动作」处理（第 12、13 章）。
  • 事务持有期间，行锁一直占着。事务里多一步慢操作，后面排队的请求就多堵一会儿。事务要短、只包数据库操作。

记住这个划分：数据库事务只能回滚数据库里的东西。出了这个进程边界，就要用工程手段对齐，而不是指望回滚。

常见误区

  • 「先 SELECT 库存够不够，再 UPDATE 扣减」：两步之间就是竞态窗口，并发下必超卖。要么条件更新，要么先锁行——不存在第三种靠运气的写法。
  • 「防重复提交靠前端禁用按钮」：刷新、重试、双标签页、直接重放请求都绕得过前端。幂等键 + 唯一约束才是服务端级别的答案。
  • 「事务越大越安全，把支付也包进来」：外部 API 一慢，锁就堵成串，而且外部调用根本回滚不了。事务的边界就是数据库的边界。
  • 「回滚能撤销一切」：回滚只对本事务的数据库修改有效。已经发出的请求、已经扣的款，要靠补偿流程。

本章练习

  1. 并发实测：把某商品库存改成 1，用两个浏览器（或脚本）同时结账，验证只有一单成功、库存为 0、没有负数。
  2. 给参考实现的下单加上 11.4 的幂等键：结账页生成请求键、订单表加列与唯一约束、action 处理重复提交。完成后连点两次提交，验证只有一张订单。
  3. 构造死锁：写一个测试事务，故意以相反顺序锁两个商品行，与正常下单并发跑，观察 PostgreSQL 如何检测并掐掉一个事务。
  4. 思考题：条件 UPDATE 打法一次扣 20 行，第 19 行失败时，前 18 行的扣减靠什么还原？
