第 16 章 全栈架构清单与进阶路线

本章目标

  • 把全书的架构决定收成一张可以贴在工位上的清单
  • 分清哪些是「任何全栈项目都成立」的通则，哪些是随业务规模变化的取舍
  • 给出学完之后的进阶路线

16.1 架构清单

分层与边界（第 1、4、13 章）

  • [ ] 按业务领域切模块，不按技术类型堆文件夹
  • [ ] 依赖只能向下：页面 → 业务 → 领域/基础设施；基础设施不反向依赖业务
  • [ ] 业务规则是纯函数、只有一份实现；多入口共用一个 service / workflow
  • [ ] 服务端边界用 server-only 等机制守住，不靠自觉

配置与数据（第 2、3 章）

  • [ ] env 运行时读取、生产环境强制校验，缺密钥拒绝启动而不是用默认值
  • [ ] 数据库连接惰性创建；构建过程不依赖数据库与生产密钥
  • [ ] 金额用最小单位整数；历史记录存快照，不实时关联「现在的样子」
  • [ ] 唯一约束、枚举/CHECK、索引都下沉到数据库；迁移有版本链

安全（第 6、7 章）

  • [ ] 密码用慢哈希；登录错误不区分「账号不存在 / 密码错误」
  • [ ] cookie 三件套：httpOnly、SameSite、Secure（按环境推导）
  • [ ] 访问控制两道门：边缘粗拦截 + 每个入口自验；他人的资源返回 404
  • [ ] 跳转地址只允许站内相对路径

写入正确性（第 8、11 章）

  • [ ] 所有输入过校验（形状 + 长度上限），校验规则与类型同源
  • [ ] 关键写操作是单个事务；防超卖用条件更新或行锁，绝不先查后改
  • [ ] 加锁按固定顺序（按 id），锁粒度匹配真实竞争点
  • [ ] 重复提交靠幂等键 + 唯一约束，不靠前端禁用按钮
  • [ ] 事务里只有数据库操作；外部调用靠状态机 + 幂等 + 补偿

集成与流程（第 12、13 章）

  • [ ] 外部 SDK 收口在一个集成层，业务代码不直接依赖第三方形状
  • [ ] 事实以异步回调为准；webhook 验签、核对金额、幂等可重入
  • [ ] 状态守卫在 service 层；审计与业务变更同事务、只追加
  • [ ] 重要通知走 outbox（或等价的可靠投递），不与业务请求同步耦合

测试与部署（第 14、15 章）

  • [ ] 测试先覆盖领域规则与最贵的不变量；CI 一条命令跑完
  • [ ] 镜像多阶段构建、非 root 运行；密钥只经环境注入
  • [ ] 迁移先行且向后兼容；备份做过恢复演练

16.2 通则与取舍，分清楚

清单里有一部分是通则——换任何技术栈、任何业务都成立：金额用整数、密码慢哈希、约束下沉数据库、幂等防重复、回调验签、审计同事务。这些不要再「结合实际灵活处理」，它们是前人用事故换来的。

另一部分是取舍——随规模与业务变化，没有标准答案：

取舍 参考实现的选择 什么情况下换
会话方案 JWT（无状态） 需要即时撤销/封号 → 数据库会话
防超卖打法 条件 UPDATE 锁内需多步判断 → 行锁
通知方式 outbox 模式（按需） 通知无足轻重 → 直接调用 + 日志
错误反馈 字段级回显 内部工具 → redirect 错误码
服务形态 模块化单体 团队/流量规模到了 → 沿模块边界拆

架构能力的高级形态，就是能说清每条决定「在什么条件下我会改主意」。把你项目里的取舍也这样列成表，写下触发条件——半年后你会感谢自己。

16.3 进阶路线

  1. 把参考实现改坏再修好：逐条去掉清单里的机制（去掉条件更新、去掉幂等键、把守卫挪回页面），用并发测试和攻击性输入复现事故，再修回来。事故亲手制造过一次，理解才是你的。
  2. 换一个业务重走全流程：用同一套分层做一个完全不同的应用（如预约系统、内容平台），观察哪些结构原样可复用、哪些要随业务变。这一步能把「这个项目的写法」提炼成「你的架构直觉」。
  3. 补齐生产化缺口：限流、结构化日志与追踪、数据库会话撤销、定时任务（超时关单、对账）、多环境部署流水线。参考实现 README 的「上线前还需要」就是现成的题目单。
  4. 读官方文档的架构章节：Next.js 的数据获取与缓存文档、PostgreSQL 的事务隔离与锁文档、Stripe 的 webhook 最佳实践。框架文档里的一手说明，比二手总结更耐用。

结尾的话

全栈架构没有银弹，只有一系列在约束下做出的、能说清理由的决定。这本教程希望留给你的不是某个项目的写法，而是一套提问顺序：先问业务前提，再看分层落点；先列不变量，再选机制；先想失效与重复，再写正常路径。 顺序对了，具体技术换代时，你的判断不会过期。

最后一组练习

  1. 拿你手边任何一个在维护的项目，对照 16.1 清单逐条打分，列出差距最大的三条，并为每条写一句整改方案与验证方法。
  2. 挑 16.2 取舍表里的一行，为你的项目写下「当前选择 + 换的触发条件」，放进项目的 README 或 ADR。
  3. 回顾全书每章的「常见误区」，挑出你真实犯过的一条，写一段复盘：当时的现象、根因、后来怎么修的。
